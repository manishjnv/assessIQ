## Z-50: organisation switch for the Distinction wording

**What changed**

- Migration `modules/02-tenancy/migrations/0205_tenant_settings_certificate_show_distinction.sql` adds `tenant_settings.certificate_show_distinction BOOLEAN NOT NULL DEFAULT FALSE`. The migration is additive and idempotent.
- `modules/02-tenancy/src/service.ts` has `getCertificateShowDistinction` and `updateCertificateShowDistinction`. The update locks the row, writes one `tenant.settings.updated` audit row with before and after values, and does nothing (no audit row) when the value does not change.
- API: `PATCH /api/admin/tenant-settings/certificate-show-distinction` with body `{ "enabled": boolean }`. It uses the `adminFreshMfa` pre-handler and checks the admin role inside the handler as well. `GET /api/admin/tenant-settings` returns the field.
- `modules/18-certification/src/display.ts` adds `certForDisplay` and `applyDistinctionSetting`. They return a display copy with the tier set to `completion` when the switch is off. The copy is used for wording only. It is never signed, verified or stored.
- The display copy is applied to the PDF route, the public verify page (including JSON-LD and the OG description), `og.svg`, `og.png` and the candidate certificate list (`listForUser`). The admin list still shows the stored tier.
- UI: a "Certificates" checkbox on Settings, Results tab, with the same fresh-MFA step-up flow as `result_release_mode`. Help id `admin.tenant_settings.certificate_show_distinction`.
- Wording fix: the admin `certificates.tsx` page said "70%+" in two places. It now says "passed".

**Why**

The owner decided that every candidate who passes gets a certificate. The word "Distinction" (90 percent or more) appears only when the organisation admin enables it. The stored tier stays, so no information is lost and the setting can change later.

**Considered and rejected**

- A per-assessment switch. The brief said tenant setting, and one switch for the organisation is easier to explain to candidates.
- Hiding the tier by changing the stored value. This would break the HMAC and lose history.

**Not included**

- No change to the issue logic (that is Z-39).
- The share text and the result email never name the tier, so they needed no change.
- Share images are cached for one hour (`cache-control: public, max-age=3600`). After a toggle, an old image can stay for up to one hour. This is documented in `docs/14-credentialing.md`.

**Downstream impact**

`docs/02-data-model.md`, `docs/03-api-contract.md`, `docs/14-credentialing.md` and the SKILL.md files of modules 02 and 18 are updated. Help seed has one more row.

**Review**

Sonnet takeover gate: ACCEPT. No tier mint, no cross-tenant read, no render path that skips the display copy. The commit carries the `Adversarial-Review` trailer.

## Z-39 tails: tier upgrade and one counting attempt per candidate

**What changed**

- `issueCertificateOnRelease` in `modules/18-certification/src/service.ts` computes the tier from the released attempt's own score. When a live certificate from an earlier attempt exists, a higher tier upgrades it through the existing compare-and-swap path: same credential id and verify URL, new HMAC, one `certification.cert.upgrade` audit row. An equal or lower tier returns the kept certificate with no audit row. A transaction advisory lock on candidate plus assessment serialises concurrent releases.
- Gate follow-ups (`bea8a8b0`): the upgrade `UPDATE` in `repository.ts` skips revoked rows (`AND revoked_at IS NULL`), and the earlier-certificate lookup has `ORDER BY c.issued_at`.
- `modules/00-core/src/attempt-counting.ts` adds `countingAttemptSql(alias)`. It is true for exactly one attempt per candidate and assessment: a released attempt wins over an unreleased one, then `best` takes the highest score and `latest` (the default) takes the highest attempt number. It is used in module 09 (`getCohortStats`, `getLeaderboard`) and module 15 (admin cohort report, cohort report, dashboard average and counts).
- `listAttemptsForAdmin` in module 07 returns `attempt_number` and `attempts_total`. The admin Attempts page shows an "Attempt n of m" chip when the total is above one. Older attempts stay in the list.

**Why**

A candidate who retakes and reaches 90 percent should hold the higher tier, and cohort numbers should count each candidate once.

**Rules that hold**

- Upgrade only. Never a downgrade.
- Only releasing a passing attempt of 90 percent or more can raise the tier. Neither `score_counts` (latest or best) nor `certificate_show_distinction` is read in the issue path, so a setting change after release cannot mint a tier.
- The certificate keeps the first attempt id. The attempt id is a signed identity field, so moving it was rejected.
- A revoked earlier certificate is ignored, so a later pass gets a new certificate. This is the existing Z-39 rule.

**Not changed on purpose**

The results CSV and JSONL export, `getIndividualScores`, the queue summary counts and the candidate activity feeds. No re-issue email was added, because no sender exists and a template without a sender fails `template-send-coverage.test.ts`.

**Known notes**

- The cohort queries use a correlated subquery per row. This is fine for admin on-demand reports. Watch the Home KPIs on large tenants and add an index on `attempts(assessment_id, user_id)` if needed.
- The old Z-39 text in `docs/14-credentialing.md` said a later attempt never changes a certificate. It is marked superseded.

**Review**

Sonnet takeover gate: ACCEPT with two low items (both fixed). Text-only `codex exec`: two remarks. The integer division remark was not valid because the columns are `NUMERIC(8,2)`. The revoked-certificate remark is the existing rule.

## EXP-18 part 2: review gate before students are invited

**What changed**

- Module 04, `service/review.ts`: `reviewQuestion` (Verify, Needs fix with a required note, Withdraw), `bulkVerifyPack` and `getPackReview`. Routes in `review-routes.ts`, all on the `adminOnly` chain:
  - `GET /api/admin/packs/:id/review`
  - `POST /api/admin/questions/:id/review`
  - `POST /api/admin/packs/:id/review/verify-all`
- Authorisation, checked in the handler and in the service on top of RLS: the role is `admin` or `super_admin`; the pack tenant equals the session tenant; a platform pack needs `super_admin`; an organisation pack needs `admin`.
- Every state change writes `question.review_changed` (actor, time, previous state). Bulk verify writes one row per question. Withdraw reuses `question.withdrawn`. The new action is in the module 14 catalogue.
- Bulk verify changes only `in_review` questions. It takes `expected_count`. A different current count returns 409 `REVIEW_COUNT_CHANGED` and writes nothing.
- Imports (`commitImport`, `bulkImport`) start questions as `in_review`. Clones keep the source state.
- Module 05: `inviteUsers`, `resendInvitation`, `resendInvitations` and `reopenInvitationForRetake` return `QUESTIONS_NOT_VERIFIED` when the pool holds `in_review`, `disputed` or `needs_fix` questions. Publish share-locks the pool rows (`FOR SHARE`, id order) and re-checks the frozen rows in the same transaction as the freeze. This closes the race noted on the row.
- Module 06, `startAttempt`: the same check runs right after the "assessment is active" check, before the invitation check, so the embed path is covered. An invitation sent earlier no longer lets a candidate start on a pool that later gained a Needs fix question. `assertPoolVerifiedForInvites` is exported from `@assessiq/assessment-lifecycle`.
- Editing the content or rubric of a verified question resets it to `in_review` in the same transaction, with an audit row (`content_edited`). A topic-only edit keeps the state.
- Verify and Needs fix on an archived question return 409 `QUESTION_ARCHIVED`.
- UI: page `/admin/question-bank/:id/review` and a "Review questions" button on the pack page. It shows the answer key, rationale, source and rights status. Six help ids (`admin.question_bank.pack.review` and `admin.question_bank.review.{filter,verify,needs_fix,withdraw,verify_all}`).
- Test fix `2a8fd43e`: the unit test mock of `withTenant` in `invite-email.test.ts` now returns `{ rows: [] }`. The builder ran the DB suites only, and CI found the mocked unit test.

**Owner decisions applied**

An empty (NULL) review state still passes publish for existing platform questions. There is no backfill. New tenant uploads and imports start as `in_review`.

**Not included**

EXP-17 (organisation upload) is not built. `createQuestion` by hand and AI drafts still insert NULL.

**Known gaps (ROADMAP row Z-52)**

2. `restoreVersion` keeps the review state.
3. A possible 40P01 deadlock between publish `FOR SHARE` and bulk `FOR UPDATE`. It would show as a 500 instead of a clean 409.
4. `expected_count` is a count, not an id set. One question can leave and another enter while the count stays equal.
5. The Needs fix note lives only in the audit row.
6. Nothing sets `disputed` yet.
7. Manual `createQuestion` and AI drafts still insert NULL.

**Review**
