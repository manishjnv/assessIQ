## Gap 5: a NULL review state is still written

**Today:** `createQuestion` and AI drafts insert a row with a NULL review state. The owner decided: no backfill of old rows.

| Option | What it means | Schema change | Risk |
|---|---|---|---|
| A. Leave NULL for old paths. Set `in_review` only in new paths (EXP-17 upload) | Smallest change. NULL stays a valid "not reviewed" state | None | Two meanings for "not reviewed" (NULL and `in_review`). Filters must treat NULL as in-review |
| B. Set `in_review` in `createQuestion` and in the AI draft path from now on | One rule for all new rows. Old rows stay NULL (no backfill) | None (a default in code) | AI drafts become visible in review queues. Platform staff would see them |
| C. Add a `DEFAULT 'in_review'` on the column | The database enforces it | A migration (module 04). The default changes inserts only; old rows stay NULL | Hidden behaviour change for every insert path, including tests |

**Owner question:** should every new question start as `in_review` (B or C), or only uploads (A)?

**Recommendation: B** now, in code, in the same change as EXP-17. It needs no migration, keeps the no-backfill rule, and makes one rule for new rows. Treat NULL as "legacy, not reviewed" in filters. A column default (C) can follow once all insert paths are known.

## Gap 6: the "Needs fix" note lives only in the audit row

**Today:** a reviewer's "Needs fix" text is saved only in the audit trail. A question page cannot show it. Audit rows should not hold free text (the PII rule in the audit module), so this is also a compliance issue.

| Option | What it means | Schema change | Risk |
|---|---|---|---|
| A. New table `question_review_notes` (id, tenant_id, question_id, version, state, note, author_user_id, created_at), append-only, RLS | History of notes. The audit row keeps only ids | A migration in module 04, with RLS and `docs/02-data-model.md` | Needs a UI to read and write notes |
| B. One column `review_note text` on the question (latest note only) | Smallest. The question page can show the note | A migration (one column) | Loses the history of earlier notes. Note text is rewritten on each change |
| C. Keep the note in the audit row | No change | None | Free text in audit rows; no way to show it on the question page |

**Owner question:** is the latest note enough, or do reviewers need the history?

**Recommendation: A** (append-only table). It keeps the audit row free of text, keeps the history for disputes (EXP-12), and fits the append-only habit of the project. Platform-only authoring means the table can live under platform tenant rules like the question tables. Size: S to M, one migration number from the orchestrator, help id for the note box.

## Gap 7: nothing sets `disputed`

**Today:** the state `disputed` exists in the model but no code sets it. EXP-12 (answer-key disputes) is the feature that should define who sets it.

| Option | What it means | Schema change | Risk |
|---|---|---|---|
| A. Wait for EXP-12 (design first) | No work now. The state stays unused | None | Dead state in the model for now (keep it, Rule A: do not delete a dormant feature) |
| B. Platform staff set `disputed` by hand in the review screen | A button "mark disputed" with a note (uses gap 6 table) | Depends on gap 6 | Candidates cannot raise a dispute; only staff |
| C. Candidate or organisation raises a dispute from a result | Full dispute flow | New table and routes in 05, 06 or 11; privacy and abuse limits | Large (EXP-12 size). Needs an owner design on who may dispute and what happens to scores |

**Owner question:** who may raise a dispute: staff only, the organisation admin, or the candidate?

**Recommendation: A for now, then B after gap 6.** Do not build C before EXP-12 has a design. Keep the `disputed` state (Rule A).

## Suggested order

1. Gap 5 option B, together with EXP-17.
2. Gap 6 option A (one migration), after the owner picks note history or latest only.
3. Gap 7 option B after gap 6; option C only inside EXP-12.
